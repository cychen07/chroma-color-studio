# 色序：当前处理架构与单张成本

更新：2026-11-04。这里区分已实现的事实、本机测量，以及尚未采购云服务的预算假设。

当前产品完全免费：手动调整、系统推荐与导出均直接开放。下文的成本指产品方承担的基础设施开销，不是用户价格。

## 目前在哪里计算

| 环节 | 位置 | 现有实现 |
| --- | --- | --- |
| 图片上传 | 浏览器 → 自有后端 | 最多 20 MB、2400 万像素；Sharp 处理 EXIF 方向、转换到 sRGB，生成原尺寸 PNG 与最长边 1400 的 WebP |
| 颜色识别 | 后端 | 最长边缩至 160 像素，剔除透明采样；在 D65 Lab 空间做最多 6 类 K-means 聚类，再逐一匹配 4,990 张色卡，使用 CIEDE2000 色差 |
| 中文色名与建议 | 后端规则 | 按色相、明度、饱和度给采样色命名；按亮度、冷暖、主色系选择预设。建议文案由模板拼接 |
| 修改与预览 | 浏览器 Web Worker + Canvas | 风格、强度、手动参数变化在本机计算，不因每次拖动调用后端，也不请求大模型 |
| 收藏方案 | 浏览器 localStorage | 保存风格、强度、全部手动参数和色值；不上传新图片 |
| 导出 | 后端 CPU | 校验图片所属会话、有效期与参数，读取原尺寸 PNG，应用共享算法，免费编码返回 PNG/JPEG |
| 原图保管 | 后端磁盘 + SQLite | 原尺寸 PNG、预览 WebP 与元数据保存约 24 小时；每 10 分钟清理到期数据。导出文件在内存生成，不另存一份 |

参考实现：`server/analyze.mjs`、`server/index.mjs`、`src/grade.worker.js`、`shared/presets.mjs`、`shared/adjustments.mjs`。

**当前运行时没有调用任何大语言模型、多模态模型或生成式图片编辑 API，所以单张模型 API 费用为 0。** 色卡编号来自已导入数据，采样色的中文描述来自规则；色卡数据量不是模型调用量。已有示例图素材的制作也不构成每次用户处理的模型调用。

推荐是确定性规则，当前不理解“人像/美食/夕阳”等语义，不做主体分割、肤色保护、局部蒙版或 RAW 显影。若未来增加大模型，适合让它识别场景、解释推荐并输出受约束的参数；精确色值提取仍可使用当前算法。那时才应按选定模型的输入图片、token、调用次数及重试量另计费用。

## 本机实测

Apple M3、Node 24.7.0、Sharp；每种尺寸运行三次，取各阶段耗时中位数。原始记录在 [benchmark.json](benchmark.json)，使用 `npm run benchmark` 可复现。

| 项目 | 2560 × 1536，约 393 万像素 | 4000 × 3000，1200 万像素 |
| --- | ---: | ---: |
| 输入 JPEG | 0.97 MB | 2.50 MB |
| 标准化原图 PNG | 9.12 MB | 24.53 MB |
| 预览 WebP | 0.39 MB | 0.45 MB |
| 原图标准化 | 191 ms | 499 ms |
| 识色与色卡匹配 | 167 ms | 195 ms |
| 生成预览 | 176 ms | 301 ms |
| 单次预设 JPEG 导出 | 302 ms / 1.44 MB | 708 ms / 3.76 MB |
| 单次精调 JPEG 导出 | 1,355 ms / 2.34 MB | 3,428 ms / 5.52 MB |

精调例子启用了曝光、对比度、色温、橙色 HSL、锐化、颗粒、暗角。12MP 输入为示例图放大裁切后的模拟样本，并非另一张真实相机照片。图像内容、压缩率、参数和机器都会影响结果。

测量覆盖算法与编解码，不含 HTTP/TLS、磁盘 I/O、SQLite、网络传输、冷启动及并发排队。各阶段耗时不可当作云端 SLA。Sharp 多线程的累计 CPU 时间也与墙钟时间不同，JSON 中分别记录。

## 一张图要付多少钱

本地开发目前没有按张收取的外部 API 费用，也没有本项目已采购的云服务账单。电脑、电力、维护仍然有成本。正式服务最主要的项目是：

1. 固定服务器月费，或按量计算费。当前服务端调色含同步 JavaScript 像素循环，较大的精调导出会阻塞同一 Node 进程；上线时应评估工作线程/任务队列及并发容量。
2. 下载流量：预览、每次导出及首屏资源。拖动滑杆不会重复下载图片；重新进入工作台或开启另一个预览可能再次请求同一 WebP。
3. 24 小时临时存储。当前输入 JPEG 会转成较大的 PNG，必须按 PNG 大小估算，不能只按上传文件大小计算。
4. 其他实际选用服务，如对象存储请求、日志、监控、域名与备份。当前没有广告或支付流程。

按量公式：

`每张成本 = 该张承担的计算费 + 实际出站 GB × 流量单价 + 暂存 GB × 保存天数/30 × 月存储单价 + 请求及其他服务费用`

固定主机可用 `每月固定费用 ÷ 当月实际处理张数` 分摊；这时不要再重复加上同一台主机的按秒 CPU 费用。已包含在主机套餐内的硬盘/流量也不应重复计费。

### 预算示例，非云厂商报价

仅为说明数量级，假设：

- 服务器 100 元/月；月处理 30,000 张，即平均 1,000 张/天。
- 出站流量 0.8 元/GB；独立计费存储 0.12 元/GB/月，保存一天。
- 每张图传输两次 WebP 预览，导出一次 JPEG，GB 按十进制估算。
- 暂不包含页面资源、请求费、日志、支付、获客与研发；服务器容量是否够用须另做部署环境压测。

| 单张摊销 | 约 393 万像素 | 1200 万像素 |
| --- | ---: | ---: |
| 固定主机摊销 | 0.00333 元 | 0.00333 元 |
| 一天存储 | 0.00004 元 | 0.00010 元 |
| 两次预览 + 一次预设导出流量 | 0.00178 元 | 0.00374 元 |
| **预设处理合计** | **约 0.0051 元/张** | **约 0.0072 元/张** |
| **同样流量假设、改为精调导出合计** | **约 0.0059 元/张** | **约 0.0086 元/张** |

因此在上述使用量和价格假设下，可先按 **约 0.005～0.009 元/张（0.5～0.9 分）** 理解这个样本的基础设施摊销。它不是实际账单，也不是任意大小、任意流量下的单价保证。

若月处理量只有 3,000 张，单是同一台 100 元主机就摊到约 0.033 元/张；多次导出和 PNG 导出会增加流量。若迁移识色/导出到客户端，可减少服务端计算和原图传输，但要验证手机性能、内存限制与导出体验，不能仅凭桌面结果推断。

## 本轮验证

- `npm run verify`：色差基准、色卡数量、真实上传、会话隔离、直接免费 PNG/JPEG 导出，以及旧奖励接口退役。
- `npm run verify:adjustments`：光感/色彩/细节、24 个 HSL 参数、零参数恒等、Alpha 保留、颗粒确定性、参数校验，以及相同输入下浏览器数组与服务器 Buffer 的一致性。原尺寸 PNG 导出逐字节匹配共享像素管线。
- 浏览器：桌面短按、长按、松开、键盘及拖离；触摸长按/短按/取消、实际触摸拖动曝光；参数收藏与恢复、推荐重置；320/390/768/1440 像素布局检查。
- 移动验证为浏览器触摸模拟；微信小程序与 iOS/Android 真机验证仍须在对应端实施。
